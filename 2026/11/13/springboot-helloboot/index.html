阶段 3 补充知识：哪些注解会被登记进名册

范围：Spring Framework + Spring Boot 官方自带、会把「类」或「方法产物」登记进容器的注解（第三方 starter 自定义注解不在列）。Boot 4.0 无新增 stereotype 注解。

主表：类级别（靠组件扫描），按使用频率从高到低

# 注解 用在 关系（一层层追到根）
1 @Component 任何「就是个组件」的类 根本身，无上级马甲
2 @Service 业务逻辑层 @Service → @Component（1 层马甲）
3 @RestController 写 REST 接口的控制器 @RestController → @Controller → @Component（2 层马甲），另叠加 @ResponseBody
4 @Configuration 配置类（常配合 @Bean） @Configuration → @Component（1 层马甲）
5 @Repository 数据访问层 @Repository → @Component（1 层马甲）
6 @Controller 传统 MVC 控制器（返回视图） @Controller → @Component（1 层马甲）
7 @RestControllerAdvice 全局 REST 异常/响应处理 @RestControllerAdvice → @ControllerAdvice → @Component（2 层马甲），另叠加 @ResponseBody
8 @ControllerAdvice 全局异常/数据绑定处理 @ControllerAdvice → @Component（1 层马甲）
9 @SpringBootConfiguration Boot 专用「配置类」标记 @SpringBootConfiguration → @Configuration → @Component（2 层马甲）
10 @JsonComponent 注册自定义 JSON 序列化器/反序列化器 @JsonComponent → @Component（1 层马甲）
11 @Named JSR-330 标准版「组件」 非 @Component 马甲，但扫描器额外识别，等价 @Component

补充通道（不靠「类被扫描」）

通道 说明
@Bean（方法级） @Configuration/@Component 类里方法加 @Bean，方法返回值注册成 bean。
@Import 家族 @Import、@ImportSelector、@ImportBeanDefinitionRegistrar；Boot 自动配置靠它批量引入。框架作者工具。

要点

  1. 「马甲」= 元注解：@Service 内部用 @Component 标注，扫描时一路翻到 @Component 就登记。
  2. @ResponseBody 不是马甲，是叠加语义：决定「方法返回值直接当响应体」。
  3. @RestController = @Controller + @ResponseBody。
  4. 极少见：@TestComponent（测试切片）、@ManagedBean（Jakarta 遗留）。
  5. bean 默认名 = 类名首字母小写（如 HelloController → helloController）。

Spring Boot 启动时，不是把世界上所有自动配置类都叫来面试，而是先读你 classpath 上每个 jar 自带的候选清单（META-INF/spring/...AutoConfiguration.imports 文件），读到谁才评估谁。r

你项目只引了 spring-boot-starter-webmvc + spring-boot-starter-actuator。数据库那一套自动配置类（DataSourceAutoConfiguration 等）住在 spring-boot-jdbc / spring-boot-datasource 这些模块的 jar 里——这些 jar 不在你 classpath 上，所以它们的候选清单压根没被读到，于是报告里连名字都不出现。

一句话：加依赖 = 增加候选者。没引 jdbc，就没有数据库候选；引了，*DataSourceAutoConfiguration *才会出现在报告里（并且大概率被 OnClassCondition 拒——因为就算有候选，类不齐也不会录取）。

这正是实验 1「依赖 = 能力」的底层真相：能力是「候选类被 classpath 携带进来」+「条件放行」。

三个条件家族

以DispatcherServletAutoConfiguration 源码为例解释:

先看总览：这份源码里一共有哪些「条件」，各归哪个家族

挂在谁身上 注解 家族 在问什么
外层类 @ConditionalOnWebApplication(type = Type.SERVLET) Web 条件 这是个 Servlet Web 应用吗？
外层类 @ConditionalOnClass(DispatcherServlet.class) 类条件 classpath 有没有 DispatcherServlet？
嵌套类 DispatcherServletConfiguration @Conditional(DefaultDispatcherServletCondition.class) 自定义条件 用户是不是已经自己配了 dispatcherServlet？
同上 @ConditionalOnClass(ServletRegistration.class) 类条件 有没有 ServletRegistration 类？
multipartResolver @Bean @ConditionalOnBean(MultipartResolver.class) + @ConditionalOnMissingBean(name=…) Bean 条件 有 resolver 吗？名字被占用了吗？
dispatcherServletRegistration @Bean @ConditionalOnBean(DispatcherServlet.class, name=”dispatcherServlet”) Bean 条件 有那个叫 dispatcherServlet 的 bean 吗？

注意两点：

  1. 条件可以挂在三个层级上：外层类 → 嵌套配置类 → 单个 @Bean 方法。越靠外，作用范围越大。
  2. 你之前问的「三个家族」其实是四个：类条件、Bean 条件、属性条件、Web 条件，外加可以无限自定义（下面第 4 节）。

① 类条件 OnClassCondition ——「classpath 上有没有这个类」

@ConditionalOnClass(DispatcherServlet.class)问的是：classpath上有没有 DispatcherServlet这个类（不是「有没有 bean）。
项目引了 spring-boot-starter-webmvc，它传递引入 spring-webmvc，里面就有 DispatcherServlet，所以这一条 matched——这也是为什么 conditions 报告里搜 DispatcherServlet 能搜到 (1652行)。

关键区别记牢：*@ConditionalOnClass *查的是 jar 里的类在不在*，@ConditionalOnBean *查的是 容器里的 bean 在不在*。两者名字像，但查的东西完全不同。*

② Bean 条件 OnBeanCondition ——「容器里有没有这个 bean」（你贴的那条 message 的来源）

看 multipartResolver 这个 @Bean 方法：

两个条件叠加（AND），缺一不可：

  • 条件 1 @ConditionalOnBean(MultipartResolver.class)：容器里存在任意名字的 MultipartResolver bean。
  • 条件 2 @ConditionalOnMissingBean(name = “multipartResolver”)：容器里不存在名叫 multipartResolver 的 bean。

为什么这么写？注释说得很直白：「如果用户自己建了 MultipartResolver，但 bean 名起错了」。这时 Spring 帮你把那个 resolver 用规范名 multipartResolver 再注册一次，让 DispatcherServlet 能按标准名字找到它。

对照着读：

condition: OnBeanCondition ← 就是 @ConditionalOnBean 背后的实现类；

④ 进阶彩蛋：报告里每一条 message 的文字

你一定会好奇：conditions 报告里那些 did not find ... / found ... 的 message，到底谁写的？答案就在这份源码底部那两个自定义条件类里：

  1. @Conditional(DefaultDispatcherServletCondition.class) 是 Spring 最底层的条件入口（@Conditional + 一个实现了 Condition 接口的类）。所有 @ConditionalOnXxx 本质都是它的「元注解马甲」——@ConditionalOnClass 内部也是 @Conditional 指向一个 OnClassCondition。所以你看到报告里的 condition 字段（OnBeanCondition、OnPropertyCondition…）就是这些实现类的类名。
  2. getMatchOutcome 返回 ConditionOutcome.match(...) / .noMatch(...)，决定这条条件「录取 / 拒绝」。
  3. message 是 ConditionMessage.forCondition("...") 开头，message.found(...) / didNotFind(...) 逐段拼出来的。报告里你读到的每一句，就是这个 builder 拼出来的字符串。

总结:

自动配置类 = 「自带条件、条件挂在类 / 嵌套类 / @Bean 方法三个层级上的候选类」。类条件查 jar 里的类，Bean 条件查容器里的 bean（*@ConditionalOnMissingBean *专门用来「用户已提供就退让」），属性条件查开关，Web 条件查应用类型；每一条 message 都是背后那个 SpringBootCondition 的 getMatchOutcome 用 ConditionMessage 拼出来的。*/actuator/conditions *只是把这些 ConditionOutcome 汇总成 JSON 给你看。

Step4: 开启自动配置

三个注解各管一件事：

  • @AutoConfiguration：声明「我是自动配置类，别靠组件扫描，靠 imports 文件加载我」。
  • @ConditionalOnBooleanProperty(prefix = "app.greeting", name = "enabled")：总闸。挂在类级别，意味着 app.greeting.enabled 不为 true 时，整个类（连同 greeting 这个 @Bean 方法）都不被处理。
  • @EnableConfigurationProperties(GreetingProperties.class)：把 GreetingProperties 注册成 bean 并绑上 app.greeting.*，这样下面 greeting(...) 才能把它当参数注入。

Appendix - Q&A

用途：沉淀核心 Spring 主线之外的零散知识点（side knowledge）。每完成一个阶段，把该阶段产生的边角疑问追加到这里；每个 Q&A 末尾的（注释）给出可点击锚点，跳回对应的学习阶段 section。

Q1：为什么 HelloControllerV2 必须写构造器才能编译通过？

private final GreetingService greetingService; 是 final 字段。Java 规定 final 实例字段必须被「明确赋值」，合法位置只有两处：声明时直接赋值，或在构造器里赋值。两者都不写，编译器报 variable greetingService might not have been initialized（编译错误，非运行时错误）。这是纯 Java 规则，与 Spring 无关；Spring 只是借这个构造器做「构造器注入」。

（注释：对应 阶段 4：IoC 与依赖注入）

Q2：Spring 什么时候创建 HelloControllerV2？

默认作用域是 singleton 且非 @Lazy，所以在应用启动时（SpringApplication.run 的容器 refresh 阶段）就被急切实例化，而不是第一次访问 /v2 时才创建。之后访问 /v2 只是调用早已存在的对象的方法。

（注释：对应 阶段 4：IoC 与依赖注入）

Q3：final 修饰的变量的「不变性」是对象级的吗？

不是。final 只保证「引用变量」不能再指向别的对象，不保证对象内容不可变。两个 HelloControllerV2 实例 hc1、hc2 各自的 greetingService 字段是相互独立的变量，但它们的值可能指向同一个 GreetingService（默认单例时），也可能指向不同实例（prototype 作用域时）。

（注释：对应 阶段 4：IoC 与依赖注入）

Q4：Spring 默认是单例吗？

是。默认作用域是 singleton：一个 bean 定义在容器里只创建且只保留一个实例，所有注入点拿到同一个对象。需要多实例时改用 @Scope("prototype")。

（注释：对应 阶段 4：IoC 与依赖注入）

Q5：@Order 能解决“多个 bean 不知道注入哪个”的问题吗？

不能。@Order 管的是排序（集合注入 List/数组时排先后），不管消歧（单值注入选谁）。单值注入有歧义时，给候选类加 @Order 依然报 but N were found。消歧靠 @Primary / @Qualifier / @Priority。@Order 数值越小越靠前，缺省为 Ordered.LOWEST_PRECEDENCE（Integer.MAX_VALUE）。

（注释：对应 阶段 4：IoC 与依赖注入）

Q6：两个 bean 都没有 @Order 时，集合注入按什么顺序？

没有保证，不能依赖。缺省时 OrderComparator 把两者都当作 LOWEST_PRECEDENCE（平级），稳定排序保持“收集顺序”；而收集顺序来自 bean 注册/组件扫描顺序，属于实现细节，随 JDK 版本、文件系统、打包方式变化。顺序重要就必须显式标 @Order（或实现 Ordered、用 @Priority）。

（注释：对应 阶段 4：IoC 与依赖注入）

Q7：@Primary / @Qualifier / @Priority 各在什么场景用？“bean 名与注入点名字匹配（隐式 fallback）”是什么？

场景选择：@Primary 定“默认”（写在实现类上，全局——多数地方用它）；@Qualifier 定“例外”（写在注入点，局部——点名某个实现）；@Priority 定“级别”（写在类上，标准——跨容器通用或需按数值排序比大小）。纯 Spring 项目通常 @Primary + @Qualifier 组合覆盖 95% 场景；做库/框架、跨容器、要排序时上 @Priority。

隐式 fallback：单值注入找到多个候选、且没有任何消歧注解时，Spring 看注入点的名字（构造器参数名 / setter 参数名 / 字段名）是否恰好等于某个候选的 bean 名，等于就选它。这是最后一道兜底，依赖“名字巧合”，脆弱；构造器参数名需编译加 -parameters（Boot 的 parent 默认已开），字段名则始终可用。故官方建议显式用 @Qualifier，别依赖名字巧合。

（注释：对应 阶段 4：IoC 与依赖注入）
